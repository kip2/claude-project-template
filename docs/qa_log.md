## Q-001: このリポジトリを作った経緯（2026-10-24）

- **相談**: プロジェクトごとに安全ルールやドキュメントの雛形を作るのは手間。同じようなテンプレートはないか。
- **回答/検討**:
  - 部分的なものはあった（Anthropic 公式の devcontainer、Trail of Bits の推奨設定、git の誤操作を止める skill など）。ただ、ドキュメント一式と安全設定をまとめたものは見つからなかった。
  - そこで、最初のプロジェクトで作った設定を、自分用のテンプレートにすることにした。
- **決定**:
  - GitHub のリポジトリ `claude-project-template` に置く。GitHub のブランチ保護を使うため Public にする。
  - Trail of Bits の設定と git-guardrails のルールを取り込む。
  - `~/.claude` に入れる前に、入れる内容をすべてドキュメントにしてユーザーが確認する。シェルスクリプト（install.sh）は使わない。
  - 個々の決定は [design.md](design.md) の 4 章。

## Q-002: 判断事項への回答（2026-10-24）

- **決定**:
  - 権限チェックを飛ばすモードは使用禁止。
  - main への直接の push はやめる。develop を作って保護し、作業ブランチから develop への PR で取り込む。PR のマージはユーザーが行う。
  - シェル設定の編集は拒否。
  - Trail of Bits の、利用状況の送信を止める設定は入れる。
  - 会話の履歴は約半年（180 日）残す。
  - `rm -rf` はすべて止める。trash も禁止。消すときはフォルダ単位などで確認してから消す（ファイルは Claude が 1 つずつ確認して消し、フォルダはユーザーが消す）。

## Q-004: GitHub への登録（2026-10-24）

- **相談**: このリポジトリを GitHub に登録したい。コミットのメールアドレスは Gmail でよいか。ダミーでもよいか。
- **回答/検討**:
  - Public リポジトリでは、コミットの作者のメールアドレスを誰でも読める。収集されてスパムの原因になり、一度 push すると消すには履歴の書き換えが要る。
  - ダミーのアドレスでも動くが、GitHub がコミットをアカウントに結びつけない（アイコン・草が付かない）。
  - GitHub の noreply アドレスなら、アドレスを隠したままアカウントに結びつく。
- **決定**:
  - `kip2/claude-project-template` を Public で作る。
  - コミットのメールアドレスは、このリポジトリだけ GitHub の noreply アドレスに設定する。
  - 最初の push は、設計どおりユーザーが `--no-verify` で行う。

## Q-005: GitHub 側の守りと、push 前の確認（2026-11-01）

- **相談**: ミスや暴走があっても GitHub 側で止まるようにしたい。ローカルの Claude の操作でも、関連するコマンドの前にリモートの保護が有効かを確認し、なっていなければユーザーに設定を頼むようにしたい。Claude 専用の権限を絞ったトークン、トークンを渡すラッパー、gh の権限ルールの追加（line-bot での相談）も取り込めるか。他に入れたほうがよいものはあるか。
- **回答/検討**:
  - 確認は安全フックの中で行うのがよい。Claude に ruleset の読み取りを許さずに済み、Claude が確認を飛ばせない。
  - ラッパーは、Claude がラッパー自体を実行できるため、トークンを完全には隠せない。トークンの文字列を Claude から隠し切ることは難しい。本当の守りは、権限を絞ったトークンと GitHub 側のルールに置く。
  - 追加で入れるとよいもの：シークレットスキャンの push 保護、Actions の権限を読み取りのみ、既定のブランチを develop、自動マージをオフ、メールアドレスを含む push の拒否、gh / git の権限ルールの追加、pre-push でのシークレット検査、トークンの期限の管理。
- **決定**:
  - push / PR 作成の前に、安全フックがリモートの保護を確認する。確認できなかったときは止めて、ユーザーに聞く。
  - Claude 専用の権限を絞ったトークン（Fine-grained PAT）を使う。ラッパーは入れない。
  - ユーザーはローカルの gh をほとんど使わないので、この PC の gh のログインそのものをそのトークンに置き換える。リポジトリの作成やブランチ保護の登録は GitHub の画面で行う。
  - 追加で挙げた項目はすべて入れる。
  - 詳細は [design.md](design.md) の 6 章。

## Q-006: GitHub の設定をスクリプトで 1 回で行う（2026-11-01）

- **相談**: 新しいプロジェクトのたびに、GitHub の画面を探しながら設定するのは面倒。管理用のログインを用意し、ruleset の登録などを 1 回で行うスクリプトにしたい。トークンの対象への追加は API でできないので、スクリプトがブラウザを開き、何をすればよいかをシェルに表示したい。Private のリポジトリも使いたいので、Private なら分岐して作業を続けてほしい。
- **回答/検討**:
  - Actions の権限と自動マージは、新しいリポジトリでは最初から安全な値になっている。それでもスクリプトで明示的に設定する。
  - 管理用のログインを PC に置きっぱなしにすると、強い権限の認証情報がずっと残る。スクリプトの間だけ一時フォルダにログインし、終わったら消す形にする。
  - トークンの対象に入っているかは、読み取りでは確かめられない（Public のリポジトリは対象外でも読める）。そこで、最初の push が通るかで確かめ、失敗したら手順を表示して待つ。
  - 無料プランの Private では、ruleset とシークレットスキャンの push 保護が使えない。スクリプトは試して、断られたら飛ばして続ける。GitHub 側の最後の砦がないため、守りはローカルだけになる。
  - Private で GitHub 側の保護がないとき、今の安全フックは Claude の push を必ず止める。そこで「毎回ユーザーに確認を出す」に変える。
- **決定**:
  - 管理用のログインは、スクリプトの間だけにする。
  - Private で GitHub 側の保護がないときは、Claude の push と PR 作成のたびに確認を出す（止めはしない）。
  - スクリプトは Claude には実行させない（安全フック、権限ルール、スクリプト自身の確認）。
  - 詳細は [design.md](design.md) の 6.10。

## Q-007: 安全装置が実際に働くかの検証（2026-11-01）

- **相談**: gh などの安全装置がちゃんと働くかを検証してほしい。
- **回答/検討**:
  - 働いていたもの：
    - `test-guard.sh` はリポジトリ版・`~/.claude` 版ともに 157 件すべて成功。`~/.claude` の中身（フック・skill・settings の権限とフック）はリポジトリと一致。
    - このセッションで実際に止まった：`gh pr merge`、`gh auth token`、`gh api -X DELETE`、`git push origin develop`、`GH_TOKEN=`、`github-setup.sh` の実行。
    - GitHub 側：main / develop の ruleset が有効で、自分は例外（bypass）ではない。既定のブランチは develop、自動マージはオフ。gh は Fine-grained のトークンで、git も `gh auth git-credential` 経由で同じトークンを使う。
    - `core.hooksPath` は `.githooks`。pre-push は main / develop への push を拒否する。
  - 見つかった穴（フックの正規表現をすり抜ける書き方）：
    1. `git -C . push` / `git -c x=y push` / `git --no-pager push`：安全フックが push と判定せず、main / develop の確認と GitHub 側の保護の確認を飛ばす。権限ルールの確認（`git push *`）も出ない。残る守りは pre-push と GitHub の ruleset だけ（無料プランの Private は pre-push だけ）。`git -C . commit` も同様（pre-commit で止まる）。
    2. `/usr/bin/gh pr merge`、`"gh" pr merge`：安全フックをすり抜ける（実地では権限の層で拒否された）。
    3. `$(gh auth token)`、`` `gh auth token` ``、`gh auth token|cat`（空白なし）：安全フックをすり抜ける（実地では権限の層で拒否された）。`gh auth status --show-token`、`git credential fill` もトークンを表示できるが、止めていない。
    4. `gh alias set`（マージなどを別名にできる）、`gh extension install`（任意のコードを入れる）を止めていない。
    5. スクリプトに書いて実行すると、フックは中身を見られない（検証自体がこの形で行えた）。正規表現では塞げない。
  - GitHub 側の残る危険：ruleset は「PR を経ること（承認 0 件）」なので、ローカルの守りをすり抜けた場合、Claude 用トークン（Contents・Pull requests の書き込み）で PR をマージできる。1 人で使うリポジトリでは承認を必須にできない。
  - 確かめられなかったもの：シークレットスキャンの push 保護（Claude 用トークンでは `security_and_analysis` が読めない）。design.md 6.9 の「サンドボックスありのプロジェクトで、フックから gh を使えるか」。
  - その他：トークンの期限が 2027-06-01 で、README の目安（30〜90 日）より長い。
- **決定**:
  - 穴の 1〜4 を塞ぐ。書き方ごとにルールを足すのではなく、判定の前にコマンドを正規化する（引用符・パス・git の全体オプションを取り除く）。権限ルールにも同じ禁止と確認を足す。
  - 5 と、GitHub 側で PR のマージを止められないことは、残る危険として受け入れる。
  - 詳細は [design.md](design.md) の 6.11。
