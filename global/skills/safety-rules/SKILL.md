# 安全ルールの管理

安全ルールは 2 層に分かれている。変えるときは、どちらの層に入れるかを必ず先に決める。

| 層 | 効く範囲 | ファイル |
|---|---|---|
| **ユーザー全体** | このPCのこのユーザーの、すべての Claude Code | `~/.claude/settings.json`（権限ルール）、`~/.claude/hooks/guard-bash.sh`（安全フック）、`~/.claude/hooks/check-remote-protection.sh`（GitHub 側の保護の確認） |
| **プロジェクト** | そのプロジェクトだけ | `./.claude/settings.json`（サンドボックス・許可ドメイン・追加の権限ルール）、`./.claude/strict-settings.json`（安全モード起動用。許可ドメインを `settings.json` と揃える）、`./.githooks/`（git 自体のフック） |

迷ったときの決め方：

- どのプロジェクトでも危ないもの（権限昇格、削除、git の破壊的な操作、認証情報）→ ユーザー全体
- そのプロジェクトの事情によるもの（通信先、パッケージの操作）→ プロジェクト

元にしているテンプレートリポジトリは `claude-project-template`。ユーザー全体の層を変えたら、テンプレートリポジトリの `global/` も同じように直し、作業ブランチから PR を出す。

## スクリプト

| スクリプト | 用途 |
|---|---|
| `bash ~/.claude/skills/safety-rules/scripts/show-rules.sh [プロジェクトのディレクトリ]` | 両方の層のルールを一覧表示する |
| `bash ~/.claude/skills/safety-rules/scripts/test-guard.sh [フックのパス]` | 安全フックのテスト（196 件以上。GitHub 側の保護の確認は偽の gh で試すので、ネットワークに出ない） |
| `bash ~/.claude/hooks/check-remote-protection.sh <ディレクトリ> push` | push 先の GitHub 側の保護を確認する（安全フックも push / PR 作成の前に使う） |
| `bash ~/.claude/skills/safety-rules/scripts/sync-safety-doc.sh [--check]` | プロジェクトの `docs/05_safety.md` のルール一覧を作り直す（`--check` を付けると点検だけ） |

## 一覧を見たいと言われた場合

`show-rules.sh` を実行し、結果を日本語で分かりやすくまとめて伝える。

## 点検してと言われた場合

1. `test-guard.sh` を実行する。
2. プロジェクトの中なら `sync-safety-doc.sh --check` を実行する（JSON が壊れていないか、許可ドメインが 2 つの設定ファイルで一致しているか、ドキュメントが最新か）。
3. `show-rules.sh` の「git のフック」が「有効」になっているか確認する。
4. `show-rules.sh` の「GitHub」欄で、push 先の保護が「有効」か、トークンの残り日数が 7 日以上あるかを確認する。サンドボックスの中で「確認できない」と出たら、ユーザーに自分のターミナルで `show-rules.sh` を実行してもらう。
5. 問題があればその内容と直し方を伝える。勝手には直さず、直してよいか確認する。

## ルールを追加・削除する場合

1. **記録する**: プロジェクトに `docs/04_qa_log.md` があれば、何を・なぜ変えるかを追記する。
2. **現状を確認する**: `show-rules.sh` を実行し、すでに同じルールがないか見る。
3. **層を決める**: 上の決め方で決め、ユーザーに確認する。
4. **方法を決める**:
   - コマンドを止めたい → `permissions.deny` に `Bash(コマンド *)` を足す。`&&` や `|` の途中に書かれても止めたいなら、安全フックにも `check` の行を足す（削除に関するものは `check_del`）。
   - 実行前に確認を出したい → `permissions.ask` に足す。
   - ファイルを読ませたくない → `Read(パス)` を deny に足す。書かせたくない → `Edit(パス)` を足す。
   - パスの書き方: `./x` はプロジェクトから見た相対パス、`~/x` はホーム、`//x` は絶対パス。`!` で除外する書き方は**使えない**。
   - 通信を許可したい → プロジェクトの `settings.json` と `strict-settings.json` の **両方** の `allowedDomains` に足す。
5. **ルールを緩める変更**（deny や ask から外す、ドメインを足す、フックのルールを外す）の場合は、変更内容と、それで何が危なくなるかを具体的に示し、**ユーザーが明示的に OK してから**編集する。
6. **編集する**: Edit ツールで編集する（設定ファイルとフックはサンドボックス内から書き換えられないため、`sed` やスクリプトは使わない）。編集時に確認が出るのは仕様。
7. **安全フックを変えた場合はテストを足す**: `test-guard.sh` に、止めるべき例を `check DENY <場所> "..."` で、止めてはいけない似た例を `check ALLOW <場所> "..."` で、それぞれ 1 つ以上足す。
   - 注意: テストしたいコマンドを Bash に直接書くと、安全フックがそのテスト自体を止めてしまう。ケースは必ずファイルに書いてから実行する。
8. **確認する**: `test-guard.sh` を実行し、`jq -e . <編集した JSON>` で JSON が壊れていないか確認する。プロジェクトなら `sync-safety-doc.sh` でドキュメントを作り直す。
9. **変更履歴に書く**: プロジェクトなら `CHANGELOG.md` の `[Unreleased]` → `### セキュリティ` に、日付付きで追記する。
10. **報告する**: 変えた内容、テスト結果を伝える。反映されていないようなら `/hooks` を開くか Claude Code を再起動するよう伝える。

## やってはいけないこと

- ユーザーの明示的な指示なしにルールを緩めること。
- サンドボックスの `enabled`、`allowUnsandboxedCommands`、`failIfUnavailable` と、`disableBypassPermissionsMode` を変えること（指示があっても、何が危なくなるかを先に説明する）。
- `excludedCommands`（サンドボックスの外で動かすコマンド）を広げること（`gh *` や `docker *` のような広い指定は特に危ない）。
- `docs/05_safety.md` の `BEGIN:rules`〜`END:rules` の間を手で編集すること。
